# 근거관문: 근거·계산·승인 경계 검증

이 문서는 성공 시연만으로 드러나지 않는 약점을 재현한 기록이다. 원문 문자열과 파일 지문이 맞아도 **같은 분석의 조건인지, 그 논문의 자료인지, 행이 사람을 뜻하는지**는 별도 확인이 필요했다. 계산 자체와 승인 결과의 표시도 따로 검증했다.

공격 자료는 전부 합성이다. 제품의 데이터 경로를 격리된 합성 등록부로 연결했으며 제품 업무 함수를 교체하지 않았다. 실제 논문 오류 발견, 실제 모델 오판, 사용자 승인 완료, 범용 AI 대비 우위로 해석할 수 없다. 모델 호출은 0회이며 Git 조회와 실행기의 네트워크 사용 범위를 구분한다.

## 우선순위가 높은 관측

### 1. 잘못 등록된 의미 연결이 계산까지 이어짐

잘못된 등록 위치, 다른 표의 인용, 다른 실험의 CSV, 한 사람의 반복 방문을 사람 수로 해석한 등록은 실제 수동 파이프라인에서도 계산과 승인 가능 상태까지 이어졌다. 등록부를 시험자가 만든 것이 전제다. 임의 사용자 입력만으로 올바른 등록부를 우회했다는 결과는 아니다.

보호 대조에서는 등록부를 올바르게 두고 후보 위치만 변경했을 때 `REGISTERED_FIELD_MISMATCH_SOURCE_LOCATION`으로 차단되고 계산이 실행되지 않았다. 전파 사례에서도 `human_approval.approved=False`, `human_semantic_confirmed=False`였다.

필요한 보완은 인용 존재 검사 이상의 연결 계약이다. 대상 주장과 분석 식별자를 먼저 고정하고, 모집단·관측 단위·시점·결과변수마다 실제 문단/표/행을 연결해야 한다. 자료와 논문의 연결 근거도 별도로 남겨야 한다. 서로 다른 위치라도 같은 분석을 설명하는 Methods와 결과표는 허용해야 하며, 다른 분석의 정의가 다르다는 이유만으로 모순 처리하면 안 된다.

### 2. 승인 재계산 후 결과의 표시가 갱신되지 않음

합성 정상 계산은 20이었다. 승인 전 보고서의 계산 표시를 999로 변경하고 실제 `approve_report`를 호출했을 때, 재계산·주장에는 20을 사용하면서 승인 반환의 `calculation.calculated_value`에는 999가 남았다. `within_tolerance=False`, 미실행/잘못된 행 수·분모·엔진 표시를 넣은 두 대조도 승인 반환에 남았다.

이는 격리된 승인 함수의 합성 시험이다. 실제 사람이 해당 잘못된 숫자를 보고 승인했다거나, UI에서 그 변조가 가능하다는 입증은 아니다. 진짜 보고값이 999인 충돌 입력은 `can_approve=True`만 바꿔도 `APPROVAL_ARITHMETIC_CONFLICT`로 차단됐다.

최소 수정은 승인 진입점이 다시 만든 `validation`과 `calculation`을 반환 보고서에도 대입한 뒤 사람 확인 표시를 기록하는 것이다. 계산값 하나만 덮는 대신 전체 파생 결과를 교체해야 행 수·분모·실행 상태가 함께 일치한다. 수정 적용 여부와 회귀 결과는 별도 상태로 관리한다.

### 3. 큰 정수·작은 허용오차의 수용 경계

`[9007199254740992, 9007199254740994]`의 정확한 평균은 `9007199254740993`이다. 보고값을 이 정수로 주고 허용오차를 0으로 두었을 때, 실제 계산 표시 `9007199254740992.0`, 차이 `0.0`, 수치 일치가 반환됐다. 정수 보고값을 float 연산에 섞으며 표현 손실이 사라진 차이처럼 취급된 것이다.

또 다른 입력에서는 허용오차 0인데 차이 `5e-13`을 수용했다. 현재 비교식의 고정 `abs_tol=1e-12`가 선언 허용오차를 넓힌다. `_calculate`와 `core.verify`를 함께 고쳐 두 경로의 판정을 일치시켜야 한다. 정밀도를 지원하지 못하는 경우에는 명시적 검토 상태로 차단하는 편이 타당하다. `0.7 ↔ 0.8, tolerance=0.1` 같은 정상 경계의 이진 표현 잔차도 회귀에 포함해야 한다.

필터 정규화로 선택 행이 늘어난 별도 사례는 분모 불일치가 차단했다. 이 보호를 무시하고 모든 정규화 사례를 승인 우회로 세지 않았다. 반복 행의 평균은 산술 자체보다 관측 단위·가중 방식의 정의 문제로 분리했다.

## 작동한 보호와 남는 경계

- 원문/자료 지문·인용 불일치, 등록부와 후보의 위치/필터 차이, 실제 산술 충돌, 변경된 입력은 관련 진입점에서 차단됐다.
- 내보낸 본문을 옛 지문 그대로 수정하면 `REPORT_INTEGRITY_MISMATCH`였다. 실제 내보내기 함수로 지문을 다시 계산한 파일은 열렸지만 `IMPORTED_REVIEW`, 승인 `active=False`가 되어 현재 승인 권한을 복원하지 않았다. 재열기 계산도 실제 20으로 갱신됐다.
- 실제 메모리 입력 변경 검사는 `BLOCKED_CHANGED_INPUT`, 승인 `INVALIDATED/active=False`였다.
- 승인 함수의 `HUMAN_USER` 표시는 사용자 신원 인증의 증거가 아니다. 이번 시험의 승인 호출은 합성 검토자의 함수 시뮬레이션이다.
- 저장된 실행 지문 메타데이터의 변조는 시험했지만, 실제 엔진 코드 교체 후 승인 동작은 이번 25입력에 포함하지 않았다.
- 모델에 보낼 때 필요한 정의가 누락되는지 평가해야 한다. `truncated=True`만 보고 모든 자료를 막으면 정상 앞부분 정의 사례도 잃는다.

## 수정 상태와 추가 회귀

**이 게시의 제품 코드 수정은 0건이다.** 같은 파일의 다른 기술검수가 진행 중이라 공용 작업 규칙에 따라 선점을 보존하고, 승인 표시의 [최소 수정 패치](verification/0_이영_근거경계_20261001/integrity/0_이영_최소수정제안.patch)와 [회귀 제안](verification/0_이영_근거경계_20261001/integrity/0_이영_integrity_regression.py)을 인계했다. 패치는 적용 가능성 검사만 통과했고 미적용이다. 이 승인 회귀 제안 실행기도 아직 별도 실행하지 않았다. 원래 25입력 실험은 실제 실행 완료다.

수치 수정의 기대를 고정한 별도 12회귀는 **정상 5통과·교정 기대 7실패·실행 오류 0**이었다. 현재 코드의 결함을 재현한 결과로, 수정 후 통과한 시험이라고 부르지 않는다. [공개 결과](verification/0_이영_근거경계_20261001/numeric/0_이영_수치회귀_results_public.json)는 원 unittest traceback의 개인 절대경로만 상대 식별자로 바꾼 파생 자료다. 원 결과 지문과 변환 내용은 파일에 남겼고 원본은 로컬에 보존했다.

공개 프로토콜·결과·실행기의 바이트는 `.gitattributes`로 줄바꿈 변환을 막았다. Git에 실제 저장된 blob과 검사한 파일의 SHA도 비교한다. 이후 수정 검증은 최신 통합 커밋에서 별도 시각·지문으로 남겨 이 실패 기록을 덮어쓰지 않는다.

## 심사에서 입증해야 할 우위

연동 수가 아니라 **잘못된 연결을 얼마나 잡고 정상 연결을 얼마나 유지하는가**를 보여준다. 목표 주장·후보·실제 문맥을 사전에 봉인하고, 후보값을 가린 독립 조건 재추출을 별도로 비교한다. 앞선 AI의 답을 다시 확인시키는 것만으로 독립 검증이라고 부르지 않는다.

거짓 수용률, 정상 처리 범위, 승인 전후 오류, 시간·비용을 같은 입력으로 비교해야 한다. 수용 0건일 때 수용 결과의 오류율은 0%가 아니라 정의 불가다. 현재 결과는 구현 우선순위를 정하는 합성 공격 근거이며, 새로운 논문 완주나 범용 AI 대비 성능 향상은 아직 실측하지 않았다.
